# #187 설계 — 질문 3개 고정 셋을 N개 질문 셋으로 바꾼다

## 무엇을 바꾸나

#186까지 질문은 `data/questions.json`의 3개뿐이다. 정답 소요 시간을 손으로 계산해 테스트에 고정한 것은 q1(1,740초) 하나다.
이 티켓은 질문을 10개로 늘리고, 정답이 있는 질문은 전부 손 계산 값과 다익스트라 결과가 같은지 테스트로 고정한다.

- 바꾸는 stub: 질문 셋(`data/questions.json`). 답하는 쪽(`stub`·`llm`)과 채점 규칙은 그대로다
- 나머지 stub(환승 180초, 기다리는 시간 0, LLM + 도구 빈 자리)은 그대로다 <!-- style-exempt -->

## 설계 결정

| 결정 | 고른 것 | 이유 |
| --- | --- | --- |
| N | 10 (기존 3 + 새 7) | #185 리뷰 #6·#8이 미룬 경우(출발 시각만, 도착 시한만, 정답 없음)를 각각 하나씩 넣고 평범한 환승 질문을 더하면 7개다. LLM 혼자 실행 한 번에 호출 10번이라 비용 걱정이 없다 |
| 손 계산 값 | 질문마다 `hand_path`(지나는 역을 호선 구간별로 적은 목록)와 `hand_seconds`(그 구간 CSV 소요시간 합 + 환승마다 180초)를 `questions.json`에 적는다 | 티켓 실패 징후: 다익스트라 출력으로만 정답을 채우면 같은 구현끼리 맞춰 본 셈이다. 테스트는 그래프(`build_graph`)를 쓰지 않고 CSV 행을 직접 더해 `hand_seconds`를 다시 계산하고, 그 값이 `shortest()` 결과와 같은지 본다 |
| 손 계산 값이 다익스트라와 다를 때 | 둘 중 무엇이 틀렸는지 원인을 찾아 적는다. `hand_seconds`를 다익스트라 값으로 고쳐 맞추지 않는다 | 고쳐 맞추면 손 계산의 의미가 사라진다. 손으로 고른 경로가 더 느린 길이었으면 그 사실을 `hand_note`에 적고 경로를 고친다 |
| 출발·도착역이 그래프에 없는 질문 | 실행 전에 검사한다. 하나라도 없으면 그 질문 id와 역 이름을 stderr에 쓰고 exit 2. 별칭(`총신대입구`→`이수`)은 그래프와 같은 규칙으로 바꾼 뒤 검사한다 | #185 리뷰 #6. 지금은 정답 없음으로 보여 틀린 답처럼 읽힌다 |
| 도착 시한을 못 맞추는 질문 | 다익스트라 최단 경로로도 `출발 시각 + 소요 시간 > 도착 시한`이면 그 질문은 정답 없음(`truth=None`)이다 | #185 리뷰 #8. 지금은 정답 경로가 시한 초과로 찍힌다 |
| 출발 시각만 / 도착 시한만 있는 질문 | 시한을 재지 않는다(지금 동작 그대로). 테스트로 고정하고 개념 표에 적는다 | 둘 중 하나만 있으면 시한을 계산할 수 없다. 「도착 시한만」을 「언제 출발해야 하나」로 바꾸는 것은 질문 종류를 새로 만드는 일이라 범위 밖이다 |
| 리포트 | 머리에 `- 손 계산으로 확인한 정답: K/M` 줄을 더한다. M은 정답이 있는 질문 수, K는 그중 `hand_seconds`가 있는 질문 수 | 티켓 통과 기준: 리포트에 손으로 정답을 확인한 질문 수를 적는다 |
| 기존 테스트 | `test_cli.py`의 `0/3`·`q1~q3` 하드코딩을 질문 수에 맞게 고친다. `test_q1_matches_hand_count`는 새 손 계산 테스트로 합친다 | |

## 정답 없음 질문과 LLM 혼자의 파싱 실패

- #186 리뷰 fix `a0975f1`이 「`path`가 빈 목록인 JSON」을 파싱 실패로 센다
- 정답 없음 질문(q6·q7)에서 LLM이 「길이 없다」며 빈 경로를 돌려주면 파싱 실패 1건으로 잡힌다. LLM 쪽 수정은 이 티켓 범위 밖이라 그대로 둔다
- 그 경우가 나오면 어느 질문에서 왜 났는지 원문과 함께 적는다
