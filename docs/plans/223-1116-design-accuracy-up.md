# #223 설계 — LLM + 도구 정답률을 올린 뒤 도구 구성 비교를 다시 잰다

## 왜

#190 게이트는 유보였다. jw 이유: 「정답률이 이전 반려 때보다 소폭 상승했으나 여전히 낮음, 최적의 도구 수를 판단하는 건 정답률 수치가 어느정도 올라간 이후 할 필요가 있음」.

#190 재작업의 두 번째 측정(10회차) 평균 맞힌 수는 잘게 나눈 도구 4.40/10, 크게 묶은 도구 3.10/10이다.

## 공통으로 바꾸는 것 — `SYSTEM` 한 문장

q6을 풀려면 시각 비교가 필요하다. 안과 무관하게 `SYSTEM` 끝에 한 문장을 더한다:

> 출발 시각과 도착 시한이 둘 다 있으면 출발 시각에 소요 시간을 더해 시한보다 늦은지 확인하고, 늦으면 길이 없는 것이다.

- `SYSTEM`은 LLM 혼자와 세 도구 구성이 모두 쓴다. 그래서 `llm-tools`·`llm-tools-coarse` 값도 #190과 조건이 달라진다. 이번 측정에서 세 구성을 같이 다시 잰다
- 질문별 힌트가 아니라 조건 하나를 읽는 일반 규칙이다

## A안 도구 정의

- `shortest_route(origin, dest, max_transfers)` — `max_transfers`는 정수 또는 `null`(제한 없음). strict 스키마라 셋 다 required다
  - 성공: `{"path": [{"station", "line"}, …], "seconds": N, "transfers": K}`. path는 지나는 역을 빠짐없이, 갈아타는 역은 두 번(내리는 호선·타는 호선) 쓴다 — `SYSTEM`이 말하는 답 형식과 같다
  - 조건을 지키는 길이 없음: `{"no_route": true}`
  - 데이터에 없는 역: `{"error": "…", "candidates": [이름이 비슷한 역 최대 10개]}` (`find_station`과 같은 후보)
  - 별칭(`총신대입구` → `이수`)은 바꿔서 찾는다  <!-- style-exempt -->
- 도구 구성 `SEARCH_TOOLS` = `find_station`, `shortest_route` 둘
- 지시문 `SEARCH_SYSTEM` = `SYSTEM` + 「도구로 역과 두 역 사이의 가장 빠른 경로(환승 상한 반영)를 확인할 수 있다.」 + 「환승 시간은 역과 호선마다 다르다.」. `_TOOLS_TAIL`의 「경로는 직접 고른다」는 넣지 않는다 — 이 구성의 뜻과 반대다  <!-- style-exempt -->
- 시한 비교는 도구가 하지 않는다. LLM이 한다(위 `SYSTEM` 문장)

## 이번에 안 하는 것

- 질문 셋·정답·채점 규칙(`grade.py`·`_parse`). 파싱 실패 「`no_route` true + path 있음」도 그대로 둔다 — 형식 규칙을 느슨하게 하면 정답률이 오르는데 그건 이 티켓이 재려는 것이 아니다
- `llm-tools`·`llm-tools-coarse`의 도구와 지시문(공통 `SYSTEM` 한 문장 말고)
- 최적의 도구 수 판정 — 이번 측정이 그 재료를 만든다. 판정은 게이트에서 jw가 한다
- 질문 셋을 늘리는 일
